# Docker Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Que `docker compose up --build` levante la app completa (backend + frontend) desde un clon limpio, funcional en menos de 2 minutos, con carga idempotente de datos y sin `expected_results.csv` dentro de la imagen — verificado de punta a punta, no asumido a partir del scaffolding existente.

**Architecture:** El scaffolding de Docker (Dockerfiles, `docker-compose.yml`, `nginx.conf`, healthcheck, Makefile) ya existe de trabajo previo (Fase 1/3) pero **nunca se verificó que funcione end-to-end**. Este plan no reescribe esa infraestructura — la ejercita contra un build real y corrige lo que falle, y agrega la única pieza que falta por completo: `.env.example`.

**Tech Stack:** Docker, Docker Compose, el Makefile ya existente.

**Spec:** specs/06-docker.md

## Estado real del repo (contexto para el ejecutor — no volver a scaffoldear esto)

Ya existen y no deben recrearse desde cero (solo corregirse si la verificación de este plan encuentra un fallo concreto):
- `backend/Dockerfile` — multi-stage `golang:1.23-alpine` → `alpine:3.20`, `CGO_ENABLED=0`, build de `cmd/api` y `cmd/eval`, usuario no-root (`adduser -D -u 10001 app`), `EXPOSE 8080`.
- `frontend/Dockerfile` — multi-stage `node:20-alpine` (build) → `nginx:1.27-alpine`, copia `nginx.conf`, `EXPOSE 80`.
- `frontend/nginx.conf` — proxy `/api/` → `http://backend:8080/api/`, sirve el SPA con `try_files $uri /index.html`.
- `docker-compose.yml` — servicios `backend` (env vars `PORT`/`DB_PATH`/`DATA_DIR`/`JWT_SECRET`/`DEMO_EMAIL`/`DEMO_PASSWORD`/`LLM_EXPLAIN`/`ANTHROPIC_API_KEY`, volumen nombrado `dbdata`, `./data:/data:ro`, healthcheck sobre `/healthz`) y `frontend` (puerto `3000:80`, `depends_on: backend: condition: service_healthy`).
- `backend/.dockerignore` (excluye `*.db`, `.git`, `expected_results.csv`, `**/expected_results.csv`) y `frontend/.dockerignore` (excluye `node_modules`, `dist`, `.git`).
- `Makefile` — `up`/`down`/`reset`/`logs`/`test`/`eval`, ya con la firma exacta que pide spec 06 (`make eval EXPECTED=/ruta/expected_results.csv`).
- `GET /healthz` en `backend/internal/api/router.go:26` (fuera de `/api`, responde `{"status":"ok"}`).
- Carga idempotente ya implementada: `seedIfEmpty()` en `backend/cmd/api/main.go` solo carga CSVs/crea el usuario demo si la tabla `readings` está vacía — el volumen nombrado `dbdata` persiste esto entre reinicios.

Lo único que falta por completo:
- **`.env.example`** — no existe en ningún lado del repo. Spec 06 lo exige explícitamente (§Reglas #5).

Todo lo demás en este plan es **verificación real contra un build real**, no trabajo nuevo asumido de antemano — si algo falla, el task correspondiente lo corrige puntualmente.

## Global Constraints

- Nunca commitear un `.env` real (con secretos) — solo `.env.example` con valores de ejemplo/defaults seguros para demo.
- `expected_results.csv` no existe en este repo (es un archivo externo del evaluador) — la verificación de "no entra en la imagen" (Task 3) se hace confirmando que el patrón del `.dockerignore` lo excluiría, más una prueba positiva con un archivo dummy si hace falta, ya que no hay un `expected_results.csv` real disponible para probar contra él directamente.
- Cualquier corrección que este plan haga al Dockerfile/compose/nginx existente debe ser el cambio mínimo que hace pasar la verificación — no refactorizar la infraestructura existente más allá de lo que un fallo real exige.
- Todos los tiempos observados (arranque, healthcheck) se reportan con números reales medidos, no estimados.

## Review Focus

- El criterio de aceptación explícito de spec 06 es "login funcional en menos de 2 minutos desde un clon limpio" — esto requiere medir tiempo real de `docker compose up --build` desde cero (sin caché de capas), no solo confirmar que eventualmente arranca.
- "Reiniciar no duplica lecturas" es una afirmación sobre el volumen `dbdata` persistiendo entre `docker compose down` (sin `-v`) y un `up` posterior — debe probarse con un reinicio real y un conteo de filas antes/después, no inferirse de leer el código de `seedIfEmpty`.
- El nginx nunca se probó proxyando tráfico real del navegador al backend — un typo en la ruta del proxy (`/api/` vs `/api`) o un problema de CORS/headers solo aparece haciendo login real a través de `localhost:3000`, no leyendo el archivo de config.
- Las variables de entorno `LLM_EXPLAIN`/`ANTHROPIC_API_KEY` se pasan al contenedor backend pero (según el plan de Cierre) el código no las lee — confirmar que esto no rompe el arranque (variables no usadas no deberían causar error, pero hay que verificarlo, no asumirlo).
- El `Makefile`'s target `test` usa `docker run ... golang:1.23-alpine go test ./...` en vez de usar el servicio ya buildeado — puede fallar por diferencias de red/volumen respecto al Dockerfile real; debe probarse tal cual está, no solo el `docker compose up`.
